# SPACES開発日誌 — ChatGPTとのやり取りの記録

> **記録対象**：2026年10月9日ごろから、駐車場カメラのRTSP配信、Web監視、LED看板の操作UIを検討・試作するまでの会話  
> **形式**：会話の要点を時系列に編集したブログ用記録。ユーザー発言は可能な限り原文を引用し、ChatGPTの長い回答・コードは要約しています。**逐語的な完全ログではありません。**  
> **注意**：動作を本人が確認した事項と、AIが提案・作成しただけの事項を分けて記載しています。IPアドレスは当時の学内ネットワークで使っていた値です。

## はじめに — 何を作ろうとしていたのか

学校の駐車場に設置するカメラとデジタル看板を、一つのシステムで管理する「SPACES」。カメラにはRaspberry Pi 4とカメラモジュールを使い、映像をWi-FiでWindowsミニPCへ送る。最終的には4台分を約1週間保存し、ブラウザの監視画面から駐車場の様子を確認しながらLED看板の表示も変更したい。

この記録は、その仕組みをChatGPTに相談しながら組み立てていった際のやり取りを、開発の流れが伝わるよう編集したもの。

## 1. 「SSH以外にいい方法は？」— 映像転送方式から相談

**自分：**

> SSH接続やその他の方法を用いて、raspberry pi 4 からwindowsのmini pcに画像（動画）を転送し、そのmini pcで監視カメラのように閲覧する方法を教えてください。ssh以外にいい方法があれば教えてください。

**ChatGPT：** SSHやSCPは録画済みファイルの転送には適するが、監視カメラのような連続映像にはTCP/UDPによる配信やRTSPが向いていると回答。まず簡単に配信を試し、本格運用にはRTSPを使う構成を提案した。

**自分：**

> 私は学校の駐車場の監視カメラを作る役をしています。とりあえず、windows PC に蓄積して、1週間ほどのデータを蓄えます。カメラは4台と仮定して、その4台分を1週間蓄積します。また、カメラはraspberrypi4のモジュールのカメラを用いています。今、接続を確認したので、いつでも可能です。まずは、通信方法を決めるのが先ですかね

**ChatGPT：** 映像転送だけでなく、録画方式も一緒に設計すべきと説明。**RTSP + H.264** を中心とし、Raspberry Pi側で配信、Windows側で表示・録画する案を推奨した。仮の設定として1080p・15fps・4Mbpsを挙げ、4台を7日間録画する場合は約1.21TB（理論上）になると試算した。

**この時点で決まった方向性：** SSHは保守用、映像はRTSP。カメラ4台・7日分をWindowsに保存することが将来の目標。ただし、録画機能はまだ実装していない。

## 2. Raspberry PiのターミナルだけでMediaMTXを導入

**自分：**

> Raspberry PiとWindows PCは同じWi-Fiに接続します。MediaMTXを使ったRTSP通信の設定を、インストールからWindowsでの映像確認まで詳しく教えてください。今、raspberry pi に画面を接続でやっています。raspberry pi側の設定はterminalだけで楽にやりたいです。

**ChatGPT：** Raspberry Pi OSでターミナルだけでセットアップする手順を提示した。CPUアーキテクチャの確認、Camera Moduleの認識確認、MediaMTXのダウンロード、`mediamtx.yml` の作成、起動、WindowsでのVLC再生という流れ。カメラは会話中に認識を確認していた **IMX708（Camera Module 3）** を使用。

案内された初期設定の主要部分：

```yaml
rtspTransports: [tcp]

paths:
  cam:
    source: rpiCamera
    rpiCameraWidth: 1280
    rpiCameraHeight: 720
    rpiCameraFPS: 15
    rpiCameraBitrate: 2000000
```

これでRaspberry Piのカメラ映像をH.264でエンコードし、`cam` という配信パスを使う構成になった。ChatGPTは、WindowsでVLCを開いて `rtsp://<Raspberry PiのIP>:8554/cam` を再生する手順も案内した。

## 5. HTMLで監視したい — RTSPとブラウザ配信の違い

**ChatGPT：** RTSP映像は通常のHTML `<video>` にそのまま載せるのではなく、MediaMTXの **HLS（8888番）** や **WebRTC（8889番）** を利用する方法を提示。Windows上のHTMLをWebサーバーで配信し、各カメラの映像を`iframe`で埋め込む構成を案内した。

当初のアクセス例：

```text
RTSP   rtsp://172.25.19.1:8554/cam
HLS    http://172.25.19.1:8888/cam
WebRTC http://172.25.19.1:8889/cam
```

**自分：**

> **172.25.19.1** で接続が拒否されました。 hiraiterundakedona

**ChatGPT：** VLCでRTSPが動いているのに、ブラウザ用ポートでは拒否されている可能性を挙げ、`ss -lnt | grep -E '8554|8888|8889'` で待受状態を確認するよう提案。HLS・WebRTCの有効化設定も示した。

**自分：**

> konohenkouwo 1kai paste surudakede ii bunsyou wo kaite

**ChatGPT：** `mediamtx.yml` のバックアップ・上書き・再起動を一括で実行できるターミナル用コマンドを提示した。新たに提案された設定の要点は次のとおり。

```yaml
rtspTransports: [tcp]
hls: true
hlsAddress: :8888
hlsVariant: fmp4
webrtc: true
webrtcAddress: :8889
```

**ここでの注意：** 一括コマンドが提示されたことまでは会話で確認できるが、実行後にHLS・WebRTCの両方が正常動作したかの最終ログは、この会話には残っていない。

## 6. 「これ、リアルタイムじゃないね」— HLSからWebRTCを重視

**自分：**

> riarutaimu dehanaine kono ko-doha

**ChatGPT：** HLSは通常ある程度の遅延が生じるので、操作しながらリアルタイムに監視する用途にはWebRTCのほうが向いていると説明。ブラウザ向けURLを **`:8889/cam`** に変更し、HTMLの`iframe`でWebRTC画面を表示する案を示した。

```html
<iframe src="http://172.25.19.1:8889/cam"
        allow="autoplay"></iframe>
```

なお、WebRTCはネットワーク環境によって追加の通信ポートや接続性の確認が必要になることも説明された。
